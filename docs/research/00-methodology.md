# CodexCockpit 技術調査の方法

更新日: 2026-08-31

## 目的

CodexCockpit を「既存の高品質な実装を組み合わせて作る」ための調査基準を定める。候補の列挙ではなく、公式 Codex CLI を実際に動かしながら、2 人のプレイヤーが CLI 側とモデル/API 側を担当できる構成へ最短距離で到達することが目的である。

## 今回の前提

- Codex CLI は OpenAI 公式実装を使う。互換 CLI の再実装を主経路にしない。
- フロントエンドは静的配信可能な構成を保つ。
- 実プロセス、PTY、認証情報、API 中継が必要な部分には、ローカルまたは隔離済みリモートの薄い companion を許容する。
- RealtimeMarkdownEditor は再利用候補であり、無条件の土台とは決めない。
- 2 人プレイ、1 人プレイ、教材リプレイを同じイベントモデルで表現できることを重視する。
- ブラウザに共有ホストの無制限 shell を直接公開しない。

## 調査の問い

1. Codex 公式のどのプロセス、プロトコル、保存層をそのまま利用できるか。
2. terminal、PTY、workspace、Git、npm/npx のどこまでを既存 OSS に委譲できるか。
3. Codex が送るモデル要求を、人間が観察・編集・応答できる最小の API gateway は何か。
4. 高品質な Web IDE の UI 部品を、巨大な IDE 全体を抱えずに再利用できるか。
5. 2 人同期と完全な教材リプレイに CRDT が必要か、権威的イベントログで十分か。
6. RealtimeMarkdownEditor の既存コードに安全な接続点があるか。

## 証拠の優先順位

| 強さ | 情報源 | 用途 |
|---|---|---|
| A | 公式ドキュメント、公式リポジトリの現行ソース、仕様 | 機能・制約・ライセンスの確定 |
| B | 公式リリース、issue、maintainer の設計文書 | 成熟度、既知の制約、ロードマップ |
| C | 実動する第三者 OSS とそのテスト／デモ | 統合可能性と実装パターン |
| D | ブログ、比較記事、会話ログ | 候補発見のみ。重要判断には単独で使わない |

数値（stars、release 日など）は 2026-08-31 時点のスナップショットとして扱い、アーキテクチャ判断の主根拠にはしない。

## 候補の評価軸

各候補を次の観点で評価する。

- `fit`: 必要な責務にどれだけ直接一致するか。
- `reuse`: fork や大改造なしに公開 API として組み込めるか。
- `maturity`: 実運用例、テスト、リリース、保守状況。
- `license`: 商用・配布・改変時の条件を満たせるか。
- `boundary`: ブラウザ、companion、隔離 runtime のどこに置くべきか。
- `security`: shell、認証情報、ネットワーク、マルチテナントの危険範囲。
- `weight`: bundle、依存、運用サービス、学習コスト。
- `lock-in`: 特定 SaaS や非公開プロトコルに拘束されるか。

## 判定語

| 判定 | 意味 |
|---|---|
| 採用候補 | PoC の第一選択。公開 API を直接利用する |
| 条件付き採用 | 特定モードまたは隔離境界でのみ利用する |
| 参考実装 | 設計や UX を学ぶが、依存としては入れない |
| 保留 | 追加検証が必要 |
| 却下 | 今回の要件、ライセンス、重量、安全性のいずれかに合わない |

## 「車輪の再発明」を防ぐルール

- Codex の thread、turn、item、approval、履歴は app-server のプロトコルを正本にする。
- terminal escape sequence、IME、Unicode、resize は既存 terminal frontend に任せる。
- PTY、shell、Node/npm/npx は実ホストまたは隔離コンテナの既存 runtime を使う。ブラウザ内互換層は offline/demo モードに限定する。
- モデル API は既存 OpenAI 互換クライアント／型／ストリーミング規約を使い、独自形式へ早期変換しない。
- 同期データは業務イベントを正本にし、共同テキスト編集が必要な箇所だけ CRDT を検討する。
- OSS の UI を見た目ごとコピーせず、公開パッケージ、プロトコル、設計パターンを再利用する。

## 各調査文書の最低要件

1. 結論を冒頭に置く。
2. 公式または一次情報への直接リンクを付ける。
3. 採用・参考・却下を明示する。
4. ライセンス、成熟度、実験的 API、重大な安全性を隠さない。
5. CodexCockpit での具体的な接続境界を書く。
6. 未解決事項と、実コードで検証すべき spike を分ける。

## 調査サイクル

1. 六つの独立トラックで一次調査を行う。
2. 全文書を統合担当が読み、矛盾・不足・依存関係を抽出する。
3. 同じ担当へ反証または不足調査を戻す。
4. 候補比較表、参照アーキテクチャ、次の spike を統合文書として作る。
5. リンクと Markdown を検証し、一つの commit として push する。

## 入力資料の扱い

添付された既存調査は候補発見に使う。そこにある「静的・非 WASM」を絶対条件とした結論は、今回の「公式 Codex を動かす」という新しい優先順位に合わせて再検証する。特に pure-JS shell の研究は offline/demo モードには有用だが、公式 Codex の native binary を動かす主経路にはできない。
